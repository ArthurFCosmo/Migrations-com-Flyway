## 💠 O cenário: duas migrations nascendo em paralelo

Até aqui, toda migration foi criada em sequência, uma de cada vez, no mesmo branch. Em equipe isso muda: dois devs podem estar trabalhando em branches diferentes ao mesmo tempo, cada um criando a "próxima" migration sem saber o que o outro está fazendo.

```
Branch A (você)          Branch B (colega)
V5__add_telefone.sql     V5__add_data_limite_tarefa.sql
```

Os dois chamaram de `V5` — conflito óbvio de nome, resolvido na hora do merge (um dos dois renomeia pra `V6`). Mas existe um problema mais sutil: o que acontece se o `V6` do seu colega **já rodou** no banco dele antes do seu `V5` ser mergeado e rodar no ambiente compartilhado?

```
Ambiente compartilhado (banco de homologação, por exemplo)
    │
    ▼
V6__add_data_limite_tarefa.sql já aplicada (colega rodou primeiro)
    │
    ▼
Você faz merge do seu V5__add_telefone.sql
    │
    ▼
Sua aplicação sobe → Flyway vê V5 chegando DEPOIS da V6 já aplicada
```

Isso é uma migration **fora de ordem** — uma versão menor (`V5`) aparecendo depois de uma versão maior (`V6`) já ter rodado naquele banco.

---

## 💠 Comportamento padrão: bloquear

Por padrão, o Flyway recusa aplicar. O raciocínio é conservador: se `V5` fosse pra rodar antes da `V6`, e a `V6` já alterou o schema, aplicar a `V5` agora pode deixar o banco num estado que nunca existiu em nenhum ambiente de teste.

```
FlywayException: Detected resolved migration not applied to database: 5
```

A aplicação recusa subir até isso ser resolvido.

---

## 💠 `out-of-order=true`: quando faz sentido liberar

```properties
spring.flyway.out-of-order=true
```

Com essa propriedade, o Flyway passa a aceitar aplicar `V5` mesmo com `V6` já rodada — ele simplesmente executa a que está faltando, na posição correta do histórico, sem re-executar nada.

Vale usar quando as duas migrations são **genuinamente independentes** — no exemplo, adicionar `telefone` em `TB_USUARIOS` não tem nenhuma relação com adicionar `data_limite` em `TB_TAREFAS`. Rodar uma antes ou depois da outra não muda o resultado final.

```
| version | description | status |
|---|---|---|
| 6 | add data limite tarefa | já aplicada |
| 5 | add telefone | aplicada agora, fora de ordem, mas sem conflito real |
```

---

## 💠 Quando isso é perigoso

Se as duas migrations **não forem independentes** — por exemplo, se a `V6` alterasse uma coluna que a `V5` também mexe — aplicar fora de ordem pode gerar um schema diferente do que qualquer outro ambiente já validou. `out-of-order=true` não verifica isso; ele só permite a execução, a responsabilidade de garantir que é seguro é sua.

Por isso não é recomendado deixar `out-of-order=true` ligado permanentemente em produção — é mais seguro como ajuste pontual pra destravar um merge específico, revisando antes se as mudanças realmente não se cruzam.

---

## 💠 Reduzindo o problema na raiz: numeração com timestamp

Uma prática comum em equipes maiores é trocar a numeração sequencial simples (`V1`, `V2`, `V3`) por versão baseada em data/hora, o que praticamente elimina colisão de números entre branches paralelos:

```
V20260315143000__add_telefone_usuarios.sql
V20260316091200__add_data_limite_tarefa.sql
```

O formato é `AAAAMMDDHHmmss`. Como o timestamp de criação de cada migration raramente coincide entre dois devs, a ordem natural já reflete a ordem real de criação — sem precisar coordenar quem "fica com o próximo número".

Pro SGP, sozinho, a numeração sequencial simples (`V1`, `V2`...) continua sendo mais simples de acompanhar. Vale considerar o formato com timestamp no momento em que o projeto passar a ter mais de uma pessoa commitando migrations em paralelo.

---

> 💡 **Resumo:** migrations fora de ordem acontecem quando branches paralelos criam versões que chegam desalinhadas no ambiente compartilhado — o Flyway bloqueia por padrão, e `out-of-order=true` libera a execução, mas só é seguro quando as mudanças são realmente independentes. Numeração por timestamp evita o problema na raiz em projetos com múltiplos devs.
