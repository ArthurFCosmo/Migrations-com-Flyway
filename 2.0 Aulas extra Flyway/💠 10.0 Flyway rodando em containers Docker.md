## 💠 O problema: banco não está pronto quando a aplicação sobe

Rodando o SGP localmente, o MySQL já está de pé há muito tempo antes de você dar `mvn spring-boot:run` — o Flyway nunca precisa esperar nada.

Em Docker isso muda. Quando a aplicação e o banco sobem juntos via `docker-compose`, os dois containers iniciam **em paralelo**. O container do MySQL leva alguns segundos pra realmente aceitar conexões (inicializar o processo interno, criar o banco, abrir a porta) — mas o container da aplicação pode tentar conectar antes disso terminar.

```
docker-compose up
    │
    ├── Container MySQL inicia ────► ainda inicializando internamente...
    │
    └── Container SGP inicia ──────► Flyway tenta conectar AGORA
                                          │
                                          ▼
                                    Connection refused
```

O resultado é a aplicação falhando ao subir, com um erro de conexão recusada — não porque a configuração está errada, mas porque o banco simplesmente ainda não estava pronto no exato milissegundo em que o Flyway tentou.

---

## 💠 `depends_on` sozinho não resolve

A tentação natural é usar `depends_on` no `docker-compose.yml`:

```YAML
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_DATABASE: sgp
      MYSQL_ROOT_PASSWORD: root

  sgp-api:
    build: .
    depends_on:
      - mysql
```

O problema: `depends_on` sozinho garante só a **ordem de inicialização do container** — o Docker sobe o `mysql` primeiro, depois o `sgp-api`. Mas "container iniciado" não é a mesma coisa que "MySQL pronto pra aceitar conexões". O container do MySQL já conta como "iniciado" muito antes do banco de dados interno terminar de subir.

---

## 💠 A solução: `healthcheck` + `condition: service_healthy`

O jeito correto é fazer o Docker verificar ativamente se o MySQL está saudável, e só então liberar a aplicação:

```YAML
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_DATABASE: sgp
      MYSQL_ROOT_PASSWORD: root
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      timeout: 3s
      retries: 5

  sgp-api:
    build: .
    depends_on:
      mysql:
        condition: service_healthy
```

- **`healthcheck`** — o Docker roda `mysqladmin ping` a cada 5 segundos dentro do container do MySQL, tentando confirmar que o banco responde de verdade
- **`condition: service_healthy`** — muda o comportamento do `depends_on`: agora o `sgp-api` só inicia depois que o `healthcheck` do MySQL passar, não só depois que o container começar a existir

```
docker-compose up
    │
    ├── Container MySQL inicia
    │       │
    │       ▼
    │   healthcheck roda de 5 em 5s até responder
    │       │
    │       ▼
    │   Status: healthy
    │
    └── SÓ ENTÃO o container SGP inicia ──► Flyway conecta com sucesso
```

---

## 💠 Por que isso ainda não é garantia 100%

`service_healthy` reduz drasticamente o problema, mas não elimina por completo. Em ambientes mais lentos (CI/CD com recursos limitados, por exemplo), ainda existe uma janela entre o `healthcheck` responder e o MySQL estar de fato pronto pra abrir novas conexões com estabilidade.

Por isso, é comum combinar o `healthcheck` com **retry na própria aplicação**, via configuração do pool de conexões:

```properties
spring.datasource.hikari.connection-timeout=30000
spring.datasource.hikari.initialization-fail-timeout=-1
```

- **`connection-timeout=30000`** — espera até 30 segundos por uma conexão antes de desistir, em vez do padrão mais curto
- **`initialization-fail-timeout=-1`** — não derruba a aplicação se a primeira tentativa de conexão falhar; ela continua tentando em segundo plano

Essa combinação — `healthcheck` no `docker-compose` + timeout generoso no HikariCP — é o que dá margem de segurança suficiente pro Flyway conseguir rodar mesmo quando o banco demora um pouco mais que o esperado.

---

> 💡 **Resumo:** em Docker, `depends_on` sozinho só ordena a inicialização dos containers, não garante que o banco já aceita conexões — por isso o Flyway pode falhar ao tentar conectar cedo demais. A combinação de `healthcheck` (`mysqladmin ping`) com `condition: service_healthy`, reforçada por timeouts mais tolerantes no HikariCP, resolve a maior parte desses casos.
