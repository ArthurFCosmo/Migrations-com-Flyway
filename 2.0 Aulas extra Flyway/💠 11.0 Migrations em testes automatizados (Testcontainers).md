## 💠 O limite dos testes com Mockito

Nos testes unitários do SGP, o `UsuarioRepository` é mockado — você nunca conversa com um banco de verdade, só simula o retorno que ele daria. Isso é correto pro que testes unitários se propõem: isolar a lógica do Service, sem depender de infraestrutura.

O problema é que isso não prova nada sobre as migrations. Um mock não sabe se a `V4__add_coluna_telefone_usuarios.sql` da [[💠 5.0 Evoluindo o schema (V2, V3...)]] realmente cria a coluna certa, com o tipo certo, sem erro de sintaxe. Migration é SQL puro rodando contra um banco real — a única forma de testar isso de verdade é com um banco real.

---

## 💠 A analogia: ensaio geral vs simulado

Teste unitário com Mockito é como treinar uma parte da peça em casa, sozinho, sem cenário — você garante que a sua fala está certa. Testcontainers é o ensaio geral no teatro de verdade, com o cenário montado: só ali você descobre se a porta que você precisa abrir realmente existe naquele lugar.

Testcontainers sobe um **container MySQL real e descartável** só pra rodar os testes, e derruba ele no final. Nenhum banco fica poluído, nenhum mock esconde um erro de SQL.

---

## 💠 Dependência no `pom.xml`

```XML
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>mysql</artifactId>
    <scope>test</scope>
</dependency>
```

Precisa do Docker instalado e rodando na máquina — o Testcontainers usa a mesma engine Docker por baixo dos panos pra subir o container de teste.

## 💠 Escrevendo o teste de integração

```Java
@Testcontainers
@SpringBootTest
class UsuarioIntegrationTest {

    @Container
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0")
            .withDatabaseName("sgp_test");
    //    ↑ container sobe uma vez, compartilhado entre os testes da classe

    @DynamicPropertySource
    static void configurarBanco(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", mysql::getJdbcUrl);
        registry.add("spring.datasource.username", mysql::getUsername);
        registry.add("spring.datasource.password", mysql::getPassword);
        //           ↑ Spring passa a apontar pro banco do container, não pro MySQL local
    }

    @Autowired
    private UsuarioRepository usuarioRepository;

    @Test
    void deveSalvarUsuarioComSchemaAplicadoPelasMigrations() {
        Usuario usuario = new Usuario(/* ... */);

        Usuario salvo = usuarioRepository.save(usuario);

        assertNotNull(salvo.getId());
    }
}
```

O que muda em relação aos testes com Mockito da apostila de testes unitários: aqui **não existe mock nenhum** de `UsuarioRepository`. Ele é injetado de verdade, apontando pra um MySQL real dentro do container.

## 💠 O que acontece ao rodar

```
Teste inicia
    │
    ▼
Testcontainers sobe um container MySQL descartável
    │
    ▼
Spring Boot conecta nesse container via @DynamicPropertySource
    │
    ▼
Flyway detecta o banco vazio e roda TODAS as migrations, V1 até a última
    │
    ▼
Teste executa contra um schema real, criado pelas migrations reais
    │
    ▼
Container é destruído ao final — nada persiste
```

Se alguma migration tiver um erro — uma coluna com tipo incompatível, uma constraint mal formada — é aqui que ela quebra, antes de chegar em produção. Esse é o valor real do Testcontainers: ele testa as migrations junto com o código, não só o código isoladamente.

---

## 💠 Quando vale a pena

Não é substituto dos testes unitários com Mockito — é complementar. Regra prática:

| Tipo de teste | O que valida | Velocidade |
|---|---|---|
| Unitário (Mockito) | Lógica do Service isolada | Rápido |
| Integração (Testcontainers) | Comportamento real, incluindo migrations e queries | Mais lento |

Testes unitários continuam sendo a maioria. Testcontainers entra pontualmente — principalmente depois de criar ou alterar uma migration, pra validar que ela realmente funciona antes de subir pra produção.

---

> 💡 **Resumo:** mocks provam que a lógica do Service está certa, mas não validam se as migrations realmente funcionam contra um banco de verdade. Testcontainers sobe um MySQL real e descartável, deixa o Flyway aplicar as migrations de verdade, e só então roda o teste — pegando erros de SQL que nenhum mock detectaria.
