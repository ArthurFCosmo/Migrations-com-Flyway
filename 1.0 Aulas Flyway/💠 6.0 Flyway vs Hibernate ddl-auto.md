## 💠 Dois "donos" do schema não convivem bem

O Hibernate, por padrão, também sabe criar e alterar tabelas — é o que o SGP usou até agora com `ddl-auto=update`. O problema de manter isso ligado junto com o Flyway é que **os dois passam a competir pelo controle do mesmo schema**.

Pensa assim: é como ter dois responsáveis reformando a mesma casa, cada um com sua própria planta, sem conversar entre si. Um pode desfazer o que o outro acabou de fazer — ou os dois criam a mesma parede duas vezes, com pequenas diferenças.

---

## 💠 Os valores de `ddl-auto`

| Valor | O que faz | Uso com Flyway |
|---|---|---|
| `update` | Cria/altera tabelas pra bater com as entidades | ❌ Nunca — conflita direto |
| `create` | Apaga e recria o schema toda subida | ❌ Nunca |
| `create-drop` | Cria ao subir, apaga ao desligar | ❌ Nunca |
| `validate` | Só confere se entidade bate com schema, não altera nada | ✅ Recomendado |
| `none` | Hibernate não toca no schema de forma alguma | ✅ Aceitável |

A diferença prática entre `validate` e `none`: o `validate` te avisa **na hora que a aplicação sobe** se uma entidade Java e uma tabela do banco estão dessincronizadas. O `none` simplesmente ignora — se estiver errado, você só descobre quando uma query falhar em tempo de execução. Por isso `validate` é a escolha mais segura pro SGP.

---

## 💠 O erro comum: os dois "brigando"

Cenário clássico de quem está migrando um projeto pro Flyway: adiciona a dependência, cria as migrations, mas esquece de trocar o `ddl-auto`.

```properties
# application.properties — configuração incompleta
spring.flyway.enabled=true
spring.jpa.hibernate.ddl-auto=update  # ← esquecido, ainda ativo
```

O que acontece:

```
Aplicação inicia
    │
    ▼
Flyway roda a V1__criacao_tabela_usuarios.sql → cria TB_USUARIOS
    │
    ▼
Hibernate, com ddl-auto=update, também tenta "ajustar" TB_USUARIOS
    │
    ▼
Schema final não é mais só o que a migration definiu
```

O sintoma mais comum é o schema real do banco não bater com o que está documentado nas migrations — alguém olha pro `V1__criacao_tabela_usuarios.sql` esperando encontrar a definição completa da tabela, mas o Hibernate silenciosamente adicionou ou alterou algo por fora.

---

## 💠 Configuração correta no SGP

```properties
# Antes (v1, v2, v3 do SGP sem Flyway)
spring.jpa.hibernate.ddl-auto=update

# Depois (com Flyway)
spring.flyway.enabled=true
spring.jpa.hibernate.ddl-auto=validate
```

Com isso, a responsabilidade fica clara:

```
Flyway   → cria e altera tabelas (fonte da verdade do schema)
Hibernate → mapeia objeto Java ↔ linha do banco, e valida se bate com o schema
```

O Hibernate continua fazendo seu trabalho de ORM — só não decide mais a estrutura das tabelas.

---

## 💠 O que `validate` de fato confere

Na subida da aplicação, o Hibernate compara cada entidade anotada com `@Entity` contra a tabela correspondente no banco: nomes de coluna, tipos compatíveis, nullability. Se a `V4` da [[💠 5.0 Evoluindo o schema (V2, V3...)]] adicionou `telefone` na `TB_USUARIOS`, mas você esqueceu de adicionar o campo `telefone` na entidade `Usuario`, o `validate` não acusa erro — colunas a mais no banco não quebram a validação.

O inverso é que quebra: se a entidade Java tem um campo que **não existe** na tabela, a aplicação recusa subir. Esse é o principal motivo pra sempre lembrar de criar a migration **antes ou junto** de alterar a entidade.

---

> 💡 **Resumo:** Flyway e `ddl-auto=update` não convivem — um decide o schema, o outro tenta decidir também, e o resultado diverge do que está documentado nas migrations. A configuração correta é `ddl-auto=validate`: o Hibernate deixa de criar tabelas e passa só a conferir se as entidades Java batem com o que o Flyway já aplicou.
