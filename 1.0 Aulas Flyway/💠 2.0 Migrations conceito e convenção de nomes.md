## 💠 O que é uma migration

Uma migration é um arquivo `.sql` com uma mudança específica no schema do banco. Não é um arquivo genérico de "script SQL" — o Flyway exige um **nome padronizado** pra saber a versão, a ordem e a descrição de cada um.

Cada migration representa uma única alteração: criar uma tabela, adicionar uma coluna, criar um índice. Uma por mudança — nunca várias mudanças diferentes amontoadas no mesmo arquivo.

---

## 💠 Convenção de nomes

```
V{versão}__{descricao}.sql
```

- **`V`** — maiúsculo, indica que é uma migration **versionada** (a mais comum)
- **`{versão}`** — número sequencial: `1`, `2`, `3`... (pode ter subversão, tipo `1.1`)
- **`__`** — dois underscores separando versão de descrição (não é um só)
- **`{descricao}`** — em snake_case, curta e direta sobre o que a migration faz

Exemplo pensando no SGP:

```
V1__criacao_tabela_usuarios.sql
V2__criacao_tabela_projetos.sql
V3__criacao_tabela_tarefas.sql
V4__add_coluna_status_projeto.sql
```

> ⚠️ Depois que uma migration já rodou em algum ambiente (mesmo que só no seu banco local), o nome e o conteúdo dela **não mudam mais**. Se precisar corrigir algo, cria uma nova migration (`V5`) — nunca edita a `V4` retroativamente. Esse comportamento é rastreado via checksum, tema da [[💠 7.0 flyway_schema_history: como o Flyway rastreia o que já rodou]].

## 💠 Migrations versionadas vs repetíveis

Existe um segundo tipo, menos comum no dia a dia:

| Tipo | Prefixo | Roda quando | Uso típico |
|---|---|---|---|
| Versionada | `V` | Uma única vez, em ordem | Criar/alterar tabelas (DDL) |
| Repetível | `R` | Toda vez que o conteúdo do arquivo muda | Views, procedures, seeds que podem ser reaplicados |

A migration repetível não tem número de versão:

```
R__recriar_view_relatorio_tarefas.sql
```

Pro SGP, praticamente tudo que você vai criar nas próximas páginas é migration versionada — estrutura de tabela é histórico, não algo pra recriar. Repetível fica pra casos específicos que vão aparecer na [[💠 9.0 Migrations com dados (seed / DML)]].

---

## 💠 Exemplo aplicado: a primeira migration do SGP

Pensando na entidade `Usuario` que você já mapeou com JPA, a migration equivalente à criação da `TB_USUARIOS` seria:

```
V1__criacao_tabela_usuarios.sql
```

O conteúdo desse arquivo (o SQL em si) é assunto da [[💠 4.0 Primeira migration na prática]] — aqui o que importa é entender que **o nome do arquivo já carrega a versão e a intenção da mudança**, antes mesmo de abrir o conteúdo.

---

> 💡 **Resumo:** toda migration segue `V{versão}__{descricao}.sql`, representa uma única mudança de schema, e uma vez aplicada nunca é editada — só substituída por uma nova versão. Migrations repetíveis (`R__`) são exceção, usadas pra views e seeds reaplicáveis.
