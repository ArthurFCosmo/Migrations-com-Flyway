## 💠 O problema que o Flyway resolve

Até agora, no SGP, quem cria e altera as tabelas do banco é o Hibernate — via `ddl-auto`. Você muda um atributo na entidade `Usuario`, sobe a aplicação, e o Hibernate ajusta o schema sozinho.

Isso funciona bem sozinho, na sua máquina, em desenvolvimento. O problema aparece em equipe ou em produção: não existe registro de **o que mudou, quando mudou, e em que ordem**. Se dois devs alteram entidades diferentes e cada um sobe a aplicação numa hora distinta, o schema final depende de quem rodou por último — não existe uma sequência confiável.

Flyway resolve isso tratando o schema do banco como algo **versionado**, com histórico.

---

## 💠 A analogia: Git para o banco de dados

Pensa no Git. Cada commit é uma mudança incremental no código, com ordem definida, e o repositório sabe exatamente quais commits já foram aplicados no seu ambiente local.

O Flyway faz a mesma coisa com o schema do banco:

- Cada **migration** é um "commit" do banco (`V1`, `V2`, `V3`...)
- O Flyway sabe exatamente quais migrations já rodaram em cada ambiente
- A ordem é sempre respeitada — não tem como rodar a `V3` antes da `V2`
- Assim como você não edita um commit já enviado, você não edita uma migration já aplicada (isso vira tema da [[💠 5.0 Evoluindo o schema (V2, V3...)]])

Enquanto o Git versiona código, o Flyway versiona **estrutura de banco**.

---

## 💠 Onde o Flyway entra no fluxo

```
Você escreve uma migration (arquivo .sql)
    │
    ▼
Sobe a aplicação Spring Boot
    │
    ▼
Flyway verifica: essa migration já rodou nesse banco?
    │
    ├── Não → executa o SQL e registra no histórico
    └── Sim → ignora, já está aplicada
```

Isso significa que o mesmo conjunto de migrations pode rodar no seu banco local, no banco de um colega, e no banco de produção — sempre chegando no mesmo resultado final, na mesma ordem.

---

## 💠 Flyway vs `ddl-auto`: visão rápida

| | `ddl-auto` (Hibernate) | Flyway |
|---|---|---|
| Quem decide o schema | A entidade Java | O arquivo `.sql` que você escreve |
| Histórico de mudanças | Não existe | Existe (`flyway_schema_history`) |
| Confiável em produção | Não | Sim |
| Controle sobre o SQL exato | Nenhum | Total |

Isso não significa abandonar o Hibernate — ele continua sendo o ORM, responsável por mapear objeto Java ↔ linha do banco. O que muda é **quem cria e altera as tabelas**. Esse ajuste de configuração (`ddl-auto=validate`) é assunto da [[💠 6.0 Flyway vs Hibernate ddl-auto]].

---

> 💡 **Resumo:** o Flyway versiona o schema do banco como o Git versiona código — cada migration é uma mudança rastreada, ordenada e nunca alterada depois de aplicada, o que dá previsibilidade que o `ddl-auto` sozinho não oferece.
