## 💠 Escrevendo a `V1`

Com a pasta `db/migration` criada, o próximo passo é escrever o SQL de verdade. Vamos usar a entidade `Usuario` do SGP como base — ela já está mapeada com JPA, então a migration só precisa espelhar em SQL o que as anotações já descrevem.

```
src/main/resources/db/migration/V1__criacao_tabela_usuarios.sql
```

```SQL
CREATE TABLE TB_USUARIOS (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    nome VARCHAR(150) NOT NULL,
    cpf VARCHAR(14) NOT NULL UNIQUE,
    email VARCHAR(255) NOT NULL UNIQUE,
    senha VARCHAR(255) NOT NULL,
    data_nascimento DATE,
    status VARCHAR(20) NOT NULL
);
```

Repara na correspondência direta com a entidade `Usuario`:

| Anotação Java | Tradução em SQL |
|---|---|
| `@Id` + `@GeneratedValue(IDENTITY)` | `BIGINT AUTO_INCREMENT PRIMARY KEY` |
| `@Column(nullable = false, length = 150)` | `VARCHAR(150) NOT NULL` |
| `@Column(unique = true)` | `UNIQUE` |
| `@Enumerated(EnumType.STRING)` | `VARCHAR(20)` — guarda o nome do enum como texto |
| Sem anotação (`dataNascimento`) | Sem `NOT NULL` — opcional |

Esse mapeamento manual é o motivo do `ddl-auto=validate` da [[💠 3.0 Configuração no projeto Spring Boot]]: se o SQL aqui não bater com a entidade Java, a aplicação recusa a subir.

## 💠 Subindo a aplicação pela primeira vez

Com o banco vazio (sem a tabela `TB_USUARIOS` ainda) e a migration no lugar, o fluxo é:

```
mvn spring-boot:run
    │
    ▼
Flyway detecta db/migration/V1__criacao_tabela_usuarios.sql
    │
    ▼
Nenhuma migration registrada ainda → executa a V1
    │
    ▼
Tabela TB_USUARIOS criada no banco
    │
    ▼
Flyway registra a V1 como "aplicada"
    │
    ▼
Hibernate valida: entidade Usuario bate com TB_USUARIOS? Sim → aplicação sobe normalmente
```

No log do console, aparece algo como:

```
Migrating schema `sgp` to version "1 - criacao tabela usuarios"
Successfully applied 1 migration to schema `sgp`
```

## 💠 A tabela `flyway_schema_history`

Depois dessa primeira execução, o Flyway cria automaticamente uma tabela de controle no banco — é assim que ele sabe, da próxima vez, que a `V1` já rodou:

```SQL
SELECT * FROM flyway_schema_history;
```

| installed_rank | version | description | script | success |
|---|---|---|---|---|
| 1 | 1 | criacao tabela usuarios | V1__criacao_tabela_usuarios.sql | 1 |

Essa tabela é a peça central de tudo que o Flyway faz — é ela que impede a `V1` de rodar de novo na próxima vez que você subir a aplicação. O funcionamento completo dela (checksum, o que acontece se editar uma migration já aplicada) é o assunto da [[💠 7.0 flyway_schema_history: como o Flyway rastreia o que já rodou]].

---

## 💠 Rodando de novo (idempotência)

Se você parar e subir a aplicação novamente, sem criar uma `V2`, o Flyway não faz nada com a `V1` — ela já está marcada como aplicada:

```
Current version of schema `sgp`: 1
Schema `sgp` is up to date. No migration necessary.
```

É esse comportamento que torna o Flyway seguro de rodar toda vez que a aplicação sobe, em qualquer ambiente — dev, teste ou produção.

---

> 💡 **Resumo:** a primeira migration (`V1`) espelha em SQL puro o que a entidade `Usuario` já descreve via anotações JPA; ao subir a aplicação, o Flyway executa o script, registra na `flyway_schema_history`, e nas próximas vezes reconhece que já está tudo aplicado — sem repetir nada.
