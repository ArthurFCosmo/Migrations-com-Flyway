## 💠 Continuando o schema: `Projeto` e `Tarefa`

A `V1` criou a tabela de usuários. O SGP também tem `Projeto` e `Tarefa` — cada uma vira sua própria migration, na sequência:

```
V2__criacao_tabela_projetos.sql
V3__criacao_tabela_tarefas.sql
```

```SQL
-- V2__criacao_tabela_projetos.sql
CREATE TABLE TB_PROJETOS (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    nome VARCHAR(150) NOT NULL,
    descricao VARCHAR(500),
    data_inicio DATE,
    data_conclusao DATE,
    status VARCHAR(20) NOT NULL,
    id_responsavel BIGINT,
    CONSTRAINT fk_projeto_responsavel FOREIGN KEY (id_responsavel) REFERENCES TB_USUARIOS(id)
);
```

```SQL
-- V3__criacao_tabela_tarefas.sql
CREATE TABLE TB_TAREFAS (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    titulo VARCHAR(150) NOT NULL,
    descricao VARCHAR(500),
    data_criacao DATE NOT NULL,
    data_conclusao DATE,
    prioridade VARCHAR(20) NOT NULL,
    status VARCHAR(20) NOT NULL,
    id_projeto BIGINT NOT NULL,
    id_usuario BIGINT,
    CONSTRAINT fk_tarefa_projeto FOREIGN KEY (id_projeto) REFERENCES TB_PROJETOS(id),
    CONSTRAINT fk_tarefa_usuario FOREIGN KEY (id_usuario) REFERENCES TB_USUARIOS(id)
);
```

Repara que `id_usuario` em `TB_TAREFAS` não tem `NOT NULL` — reflete diretamente a regra que você já conhece da entidade `Tarefa`: uma tarefa pode não ter responsável atribuído.

Depois de rodar a aplicação, o histórico fica:

| version | description |
|---|---|
| 1 | criacao tabela usuarios |
| 2 | criacao tabela projetos |
| 3 | criacao tabela tarefas |

## 💠 Uma migration por mudança

Cada alteração de schema — mesmo pequena — vira uma nova migration. Não se edita as anteriores, não se acumula várias mudanças num único arquivo depois que o projeto já está rodando.

Exemplo: imagine que, depois da `V3`, você decide adicionar um campo `telefone` na tabela de usuários. Isso **não** entra na `V1`. Vira uma nova migration:

```SQL
-- V4__add_coluna_telefone_usuarios.sql
ALTER TABLE TB_USUARIOS
ADD COLUMN telefone VARCHAR(20);
```

E, no lado do Java, o mesmo campo entra na entidade `Usuario`:

```Java
// v1 — como era
private String cpf;
private String email;

// v2 — como ficou
private String cpf;
private String email;
private String telefone; // ← novo campo, correspondente à V4
```

As duas mudanças (SQL e entidade) andam sempre juntas — uma sem a outra quebra o `ddl-auto=validate`.

## 💠 Alterando um tipo de coluna já existente

Outro caso comum: perceber que um campo está pequeno demais. Digamos que `descricao` em `TB_PROJETOS` precise passar de `VARCHAR(500)` pra `VARCHAR(1000)`:

```SQL
-- V5__alterar_tamanho_descricao_projetos.sql
ALTER TABLE TB_PROJETOS
MODIFY COLUMN descricao VARCHAR(1000);
```

De novo: não se volta na `V2` pra mudar o `500` pra `1000`. A `V2` já rodou em algum ambiente — editá-la depois de aplicada é o erro mais comum de quem está começando com Flyway.

---

## 💠 Por que nunca editar uma migration já aplicada

O Flyway calcula um **checksum** (uma espécie de "impressão digital") do conteúdo de cada migration na hora que ela roda, e guarda isso na `flyway_schema_history`.

Se você editar o arquivo `V2__criacao_tabela_projetos.sql` depois que ele já rodou, na próxima subida da aplicação o Flyway compara o checksum salvo com o checksum do arquivo atual — eles não batem, e a aplicação **recusa subir**:

```
FlywayException: Validate failed:
Migration checksum mismatch for migration version 2
```

Isso existe porque o Flyway não sabe distinguir "seu ambiente já rodou isso" de "outro ambiente também já rodou isso com o conteúdo antigo" — o mecanismo de detecção e os comandos pra lidar com esse cenário (`repair`) são o assunto da [[💠 7.0 flyway_schema_history: como o Flyway rastreia o que já rodou]] e da [[💠 8.0 Comandos e situações comuns]].

Regra prática: **migration aplicada é passado. Mudança nova é migration nova.**

---

> 💡 **Resumo:** o schema evolui em passos — cada alteração (nova tabela, nova coluna, tipo diferente) vira sua própria migration numerada, nunca uma edição retroativa. O Flyway detecta violação disso via checksum e bloqueia a aplicação de subir.
