## 💠 A "carteira de identidade" das migrations

Na [[💠 4.0 Primeira migration na prática]] a `flyway_schema_history` apareceu de relance, com poucas colunas. Aqui é o detalhe completo — é essa tabela que dá ao Flyway memória sobre o que já rodou, quando, e se rodou com sucesso.

Pensa nela como o extrato bancário do schema: cada linha é uma transação (uma migration aplicada), com data, valor (checksum) e status. Assim como você não edita uma linha de extrato já lançada, você não edita uma migration já registrada ali.

---

## 💠 Colunas da tabela

```SQL
SELECT * FROM flyway_schema_history;
```

| Coluna | O que representa |
|---|---|
| `installed_rank` | Ordem de execução (1, 2, 3...) |
| `version` | Versão da migration (`1`, `2`, `3`...) |
| `description` | Texto extraído do nome do arquivo |
| `script` | Nome completo do arquivo `.sql` |
| `checksum` | "Impressão digital" do conteúdo do arquivo |
| `installed_by` | Usuário do banco que executou |
| `installed_on` | Data/hora da execução |
| `execution_time` | Tempo que a migration levou pra rodar (ms) |
| `success` | `1` se aplicou sem erro, `0` se falhou |

Pro schema do SGP construído até a [[💠 5.0 Evoluindo o schema (V2, V3...)]], a tabela ficaria assim:

| installed_rank | version | description | success |
|---|---|---|---|
| 1 | 1 | criacao tabela usuarios | 1 |
| 2 | 2 | criacao tabela projetos | 1 |
| 3 | 3 | criacao tabela tarefas | 1 |
| 4 | 4 | add coluna telefone usuarios | 1 |
| 5 | 5 | alterar tamanho descricao projetos | 1 |

## 💠 Checksum: como o Flyway detecta edição indevida

O `checksum` é calculado a partir do **conteúdo** do arquivo `.sql` — não do nome, não da data. Qualquer caractere alterado (um espaço a mais, uma vírgula, um `NOT NULL` removido) gera um checksum diferente.

```
V2__criacao_tabela_projetos.sql (conteúdo original)
    │
    ▼
checksum calculado: 482910573
    │
    ▼
Salvo na flyway_schema_history na primeira execução
```

Na subida seguinte da aplicação, o Flyway recalcula o checksum do arquivo atual e compara com o que está salvo:

```
Checksum salvo:    482910573
Checksum do arquivo agora: 918273645
    │
    ▼
Não bate → FlywayException: Validate failed
```

Isso é exatamente o comportamento citado como erro comum na [[💠 5.0 Evoluindo o schema (V2, V3...)]] — o checksum é o mecanismo por trás do bloqueio.

## 💠 Quando `success = 0`

Se uma migration falha no meio da execução (erro de sintaxe SQL, coluna que já existe, etc.), o Flyway registra a tentativa com `success = 0` — e a aplicação não sobe.

```
Migration V6__add_coluna_invalida.sql falhou na execução
    │
    ▼
Linha registrada na flyway_schema_history com success = 0
    │
    ▼
Flyway bloqueia qualquer nova migration até isso ser resolvido
```

Esse estado — uma migration "sujando" o histórico com falha — é justamente o cenário que o comando `repair` resolve, tema da próxima página.

---

> 💡 **Resumo:** a `flyway_schema_history` é o registro definitivo de tudo que já rodou — versão, checksum, sucesso e tempo de execução. O checksum é o que garante que uma migration aplicada não possa ser silenciosamente editada depois, e uma migration que falha fica marcada até ser corrigida.
