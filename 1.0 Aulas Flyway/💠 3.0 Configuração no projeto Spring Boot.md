## 💠 Dependência no `pom.xml`

Pra usar Flyway no SGP, o primeiro passo é adicionar a dependência no Maven:

```XML
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
```

Se o banco for MySQL (como no SGP), também é necessário o módulo específico:

```XML
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-mysql</artifactId>
</dependency>
```

> Sem o `flyway-mysql`, o Flyway até sobe, mas pode falhar ao reconhecer dialetos específicos do MySQL nas migrations.

Assim que a dependência é adicionada e o projeto é atualizado no Maven, o Flyway já **roda automaticamente** toda vez que a aplicação sobe — não precisa chamar nada manualmente no código.

## 💠 Onde ficam as migrations

O Flyway procura os arquivos `.sql` em um caminho padrão dentro de `resources`:

```
src/main/resources/db/migration/
```

Pensando na estrutura de pastas do SGP:

```
src
└── main
    ├── java
    │   └── PASTA COM O NOME DO PROJETO
    │       ├── controller
    │       ├── service
    │       ├── repository
    │       ├── model
    │       └── dto
    └── resources
        ├── application.properties
        └── db
            └── migration
                ├── V1__criacao_tabela_usuarios.sql
                ├── V2__criacao_tabela_projetos.sql
                └── V3__criacao_tabela_tarefas.sql
```

> `src\main\resources\db\migration\` criamos essa pasta aqui — não é gerada automaticamente, você cria manualmente.

Esse caminho é convenção padrão do Flyway. Dá pra mudar (propriedade `spring.flyway.locations`), mas não há motivo pra fugir do padrão sem necessidade real.

## 💠 Propriedades no `application.properties`

```properties
spring.flyway.enabled=true
spring.flyway.baseline-on-migrate=true
```

- **`spring.flyway.enabled=true`** — liga o Flyway. Já vem `true` por padrão quando a dependência está no projeto, mas é comum deixar explícito.
- **`spring.flyway.baseline-on-migrate=true`** — permite o Flyway assumir controle de um banco que já existe com tabelas (situação que aparece com mais detalhe na [[💠 8.0 Comandos e situações comuns]], junto com o comando `baseline`).

Nesse ponto também entra a mudança mais importante pro SGP: desligar o Hibernate como criador de schema.

```properties
# Antes (sem Flyway)
spring.jpa.hibernate.ddl-auto=update

# Depois (com Flyway)
spring.jpa.hibernate.ddl-auto=validate
```

Com `validate`, o Hibernate para de criar/alterar tabelas — ele só **confere** se as entidades Java batem com o schema que o Flyway já criou. Se não bater, a aplicação nem sobe. Essa relação entre os dois é o assunto central da [[💠 6.0 Flyway vs Hibernate ddl-auto]].

## 💠 O que acontece ao subir a aplicação

```
Aplicação inicia
    │
    ▼
Flyway lê src/main/resources/db/migration/
    │
    ▼
Compara com o histórico já registrado no banco
    │
    ▼
Executa as migrations pendentes, em ordem
    │
    ▼
Hibernate valida se as entidades batem com o schema (ddl-auto=validate)
```

Não existe passo manual — configurou a dependência e as propriedades, o resto é automático a cada `run`.

---

> 💡 **Resumo:** o Flyway entra no projeto via `flyway-core` (+ `flyway-mysql` pro SGP), lê migrations de `src/main/resources/db/migration`, e passa a rodar sozinho a cada subida da aplicação — momento em que o `ddl-auto` deixa de criar schema e passa só a validar.
