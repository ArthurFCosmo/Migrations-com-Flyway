## 💠 DDL vs DML: dois tipos de mudança

Todas as migrations vistas até aqui alteram **estrutura**: `CREATE TABLE`, `ALTER TABLE`. Isso é DDL (Data Definition Language) — define como o schema é.

Existe outro tipo de mudança: inserir dados. `INSERT INTO` é DML (Data Manipulation Language) — não muda a estrutura, muda o conteúdo. O Flyway trata os dois da mesma forma, como migration versionada — a diferença está só no que o `.sql` contém.

```
DDL → define a forma da tabela (colunas, tipos, constraints)
DML → preenche a tabela com linhas
```

---

## 💠 Quando faz sentido popular via migration

Nem todo dado vira migration. Cadastro de usuário feito pela aplicação (via endpoint `POST /usuario`) não tem nada a ver com Flyway — é fluxo normal da API.

Migration de dados faz sentido quando o dado é **parte do funcionamento do sistema**, não conteúdo criado pelo usuário final. No SGP, dois casos claros:

- Um usuário admin inicial, necessário pra alguém conseguir logar no sistema recém-implantado
- Valores fixos de referência, como os do enum `StatusUsuario`, se algum dia isso migrasse de enum Java pra uma tabela de domínio no banco

---

## 💠 Exemplo: usuário admin inicial

```
V6__seed_usuario_admin.sql
```

```SQL
INSERT INTO TB_USUARIOS (nome, cpf, email, senha, status)
VALUES (
    'Administrador',
    '00000000000',
    'admin@sgp.com',
    '$2a$10$examplehashedpassword', -- ← senha já em hash, nunca texto puro
    'ATIVO'
);
```

> ⚠️ Senha em migration de seed **nunca** vai em texto puro — precisa estar no mesmo formato que o Spring Security grava (BCrypt, por exemplo), senão o login desse usuário nunca funciona.

Essa migration roda uma única vez, como qualquer `V`, e fica registrada na `flyway_schema_history` igual às anteriores.

## 💠 Exemplo: valores fixos de domínio

Se `StatusUsuario` (hoje um enum Java: `ATIVO`, `INATIVO`, `BLOQUEADO`) precisasse virar uma tabela de referência no banco — cenário comum quando o front-end precisa listar os status disponíveis via API, em vez de tê-los fixos no código:

```
V7__seed_status_usuario.sql
```

```SQL
CREATE TABLE TB_STATUS_USUARIO (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    nome VARCHAR(20) NOT NULL UNIQUE
);

INSERT INTO TB_STATUS_USUARIO (nome) VALUES
    ('ATIVO'),
    ('INATIVO'),
    ('BLOQUEADO');
```

Repara que essa migration mistura DDL (`CREATE TABLE`) e DML (`INSERT`) no mesmo arquivo — aceitável quando os dois estão diretamente ligados: a tabela só existe pra guardar exatamente esses valores.

## 💠 Seed via `R__` (repetível)

Voltando à [[💠 2.0 Migrations conceito e convenção de nomes]]: se esse tipo de dado de referência muda ocasionalmente (adicionar um novo status, por exemplo), faz mais sentido como migration repetível — o Flyway reaplica sempre que o conteúdo do arquivo mudar:

```SQL
-- R__seed_status_usuario.sql
DELETE FROM TB_STATUS_USUARIO;

INSERT INTO TB_STATUS_USUARIO (nome) VALUES
    ('ATIVO'),
    ('INATIVO'),
    ('BLOQUEADO'),
    ('PENDENTE'); -- ← novo valor, arquivo mudou, Flyway reaplica no próximo start
```

Diferente da versionada, aqui não tem problema editar o arquivo depois — é exatamente esse o propósito do `R__`.

---

> 💡 **Resumo:** migrations não se limitam a estrutura — `INSERT` também é migration válida, usada pra dados que fazem parte do funcionamento do sistema (admin inicial, valores de domínio), nunca pra conteúdo gerado pelo usuário final. Dados fixos que mudam ocasionalmente cabem melhor numa migration repetível (`R__`) do que numa versionada.
