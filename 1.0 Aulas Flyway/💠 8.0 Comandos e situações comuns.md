## 💠 `repair`: consertando o histórico

Na [[💠 7.0 flyway_schema_history: como o Flyway rastreia o que já rodou]] vimos dois cenários que travam a aplicação: checksum divergente e migration com `success = 0`. O `repair` existe pra resolver exatamente isso — ele **não roda SQL nenhum**, só corrige o que está registrado na `flyway_schema_history`.

```
mvn flyway:repair
```

O que ele faz:

- Remove entradas de migrations que falharam (`success = 0`)
- Recalcula o checksum salvo, alinhando com o arquivo atual
- Não desfaz nenhuma alteração já feita no schema

> `repair` resolve o **registro**, não o schema. Se uma migration falhou no meio do caminho e deixou a tabela pela metade, o `repair` limpa o histórico — mas você ainda precisa consertar o schema manualmente ou via nova migration antes de rodar de novo.

## 💠 `baseline`: adotando Flyway num banco que já existe

Até aqui, todo exemplo partiu de um banco vazio. Mas imagina que o SGP já estivesse em produção há meses, criado originalmente com `ddl-auto=update`, cheio de usuários e projetos cadastrados — e só agora você decide adotar Flyway.

Nesse caso, não dá pra simplesmente rodar uma `V1__criacao_tabela_usuarios.sql` com `CREATE TABLE`: a tabela já existe, com dados dentro. É pra isso que serve o `baseline`.

```properties
spring.flyway.baseline-on-migrate=true
spring.flyway.baseline-version=1
```

```
Banco já existe (TB_USUARIOS, TB_PROJETOS, TB_TAREFAS com dados)
    │
    ▼
Flyway sobe e encontra um schema sem flyway_schema_history
    │
    ▼
baseline-on-migrate=true → cria a flyway_schema_history
    │
    ▼
Marca tudo até a baseline-version como "já aplicado", sem executar SQL
    │
    ▼
Migrations com versão MAIOR que a baseline rodam normalmente
```

Na prática: você cria uma `V1__baseline.sql` vazia (ou representando o schema atual só como documentação), define `baseline-version=1`, e a partir da `V2` o Flyway passa a controlar as mudanças novas — sem tocar no que já existe.

## 💠 `clean`: por que é perigoso

```
mvn flyway:clean
```

Esse comando **apaga todas as tabelas do schema** — literalmente um `DROP TABLE` em cada uma, incluindo a própria `flyway_schema_history`. É útil pra resetar um ambiente de teste do zero rapidamente.

O perigo é óbvio: se `clean` rodar apontando pro banco de produção — por engano de configuração, ambiente errado, ou variável de ambiente trocada — todos os dados do SGP (usuários, projetos, tarefas) desaparecem sem confirmação, sem backup automático, sem possibilidade de desfazer.

> Por padrão, o Spring Boot desabilita o `clean` (`spring.flyway.clean-disabled=true`) justamente pra evitar isso. Se precisar habilitar pra rodar testes locais, faça isso **apenas** no `application-test.properties`, nunca no `application.properties` principal que aponta pra produção.

## 💠 Resumo dos três comandos

| Comando | O que faz | Risco |
|---|---|---|
| `repair` | Corrige o histórico (checksum, falhas) | Baixo — não mexe em dados |
| `baseline` | Adota Flyway num banco que já existe | Médio — exige atenção na versão inicial |
| `clean` | Apaga todas as tabelas | Alto — nunca em produção |

---

> 💡 **Resumo:** `repair` conserta o histórico sem tocar em dados, `baseline` permite adotar Flyway num banco já existente sem recriar tabelas com dados dentro, e `clean` apaga tudo — por isso vem desabilitado por padrão e deve ficar restrito a ambientes de teste.
